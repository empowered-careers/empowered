## The four conventions

If you read nothing else, read these. Each one is enforced by review, not by the
compiler.

### 1. Every authenticated route is a Server Component entry

"No SEO needed" does **not** mean "no Server Component." Even `noindex` pages —
dashboard, profile, resume, assessments — use a Server Component as the page entry.

| Layer                             | Responsibility                                                                |
| --------------------------------- | ----------------------------------------------------------------------------- |
| `page.tsx` (Server Component)     | Auth check + `redirect()`, initial data fetch, metadata                       |
| `*-client.tsx` (Client Component) | State, events, TanStack Query (hydrated from `initialData`), Realtime, modals |

Three reasons this is non-negotiable:

- **Perf** — initial data ships with the HTML; no loading spinner on first paint.
- **Auth** — server-side `redirect('/login')` runs before render, so there's no flash
  of protected content.
- **RLS** — the server Supabase client carries the user's session automatically, so
  policies just work.

**No DTO layer.** Pass Supabase row types straight through to the client component.

### 2. Never import `database.types.ts` directly

`src/types/database.types.ts` is generated by `npm run supabase:types` and is not an
import target. Every enum alias, full-row alias, and column-subset type lives in
**`src/types/db.ts`**.

```ts
// ✗ never
type Status = Database["public"]["Enums"]["resume_status"];

// ✓ always
import type { ResumeStatus } from "@/types/db";
```

For list views that select a subset of columns, add **both** the SELECT column string
(e.g. `JOB_CARD_COLUMNS`) and the matching `Pick<>` type (e.g. `JobCardFields`) to
`db.ts`, and use the constant in the `.select(...)` call so the two can't drift.

When you touch an unfamiliar table, **step one is adding its aliases to `db.ts`** —
not inline-deriving them in the first file that needs them.

`db.ts` also holds unions that aren't Postgres enums, such as `CoachingProductKind`
(`coaching_products.kind` is a text column with a CHECK constraint). Those live there
as the single source of truth.

### 3. All mutations are Server Actions

Everything in `src/app/actions/` (16 files, one per domain). After a Server Action
succeeds, invalidate the relevant TanStack Query key.

### 4. Query keys come from `src/lib/query-keys.ts`

Never hardcode a string array as a query key. Add it to `queryKeys` and import it.

### Bonus: never format a date during render

This one has caused two production incidents, so it earns a rule of its own.

`toLocaleDateString` / `toLocaleString` read the **runtime's time zone**, and its
**locale** when one isn't pinned. The server renders in UTC; the visitor's browser
renders in their own zone. Any timestamp near midnight UTC therefore formats to a
different day on each side — a text mismatch that throws **React #418**. The error
boundary then replaces the entire page with "Something went wrong", and every control
on it goes dead.

Use `<LocalDate>`, `<LocalDateOrNull>`, or `useLocalDateOrNull()` from
`src/components/local-date.tsx`. They pin the server snapshot to UTC so the server
render and the hydration pass agree, then swap to the visitor's local date.

The same trap applies to anything else that differs between server and client:
`new Date()`, `Math.random()`, `window`, `localStorage`. If you genuinely need one
during render, use `useSyncExternalStore` with a stable server snapshot — that's what
the time-of-day greeting in `dashboard-header.tsx` does.

Server Components are exempt: they render once and never hydrate.

## Request flow

```
Browser
  │
  ├─ src/proxy.ts ──────────── Supabase session refresh; redirects
  │                            /dashboard → /login when signed out,
  │                            /login → /dashboard when signed in
  │
  ├─ src/app/layout.tsx ────── ThemeProvider
  │                             └ QueryProvider
  │                                └ AuthProvider
  │                                   └ ModalProvider
  │                                      ├ RealtimeNotifications  (mounts hooks)
  │                                      ├ Toaster  (Sonner)
  │                                      └ Analytics  (Vercel)
  │
  └─ Route group
       ├ (public)/  marketing — home, pricing, about, events, blog, career-assessment
       ├ (app)/     candidate app — layout.tsx is the auth + purchase gate
       ├ admin/     role='admin'
       └ employer/  role='employer'  💤 DORMANT
```

### Providers

Order matters — each depends on the one above it.

| Provider        | File                                      | Provides                               |
| --------------- | ----------------------------------------- | -------------------------------------- |
| `ThemeProvider` | `components/providers/theme-provider.tsx` | Dark/light via `next-themes`           |
| `QueryProvider` | `components/providers/query-provider.tsx` | TanStack Query + DevTools in dev       |
| `AuthProvider`  | `components/providers/auth-provider.tsx`  | `useAuth()` — user, session, `signOut` |
| `ModalProvider` | `components/providers/modal-provider.tsx` | Global modals, no prop drilling        |

### The `(app)` layout does three gates in order

`src/app/(app)/layout.tsx`:

1. **Auth** — no user → `redirect('/login')`.
2. **Role** — `role === 'employer'` → `redirect('/employer')`.
3. **Purchase** — if `PURCHASE_GATE_ENABLED === "true"` and the user is neither an
   admin nor holder of an enrollment → `redirect('/invite')`. Entitlement is read
   from `enrollments`, never from user metadata, which the browser session can write
   itself. `/invite` offers two ways through: redeem `BETA_INVITE_CODE` for a comp
   "Beta Access" enrollment, or buy something. Both writers
   (`redeemInviteCode()`, `handleCheckoutCompleted()`) use the service-role client,
   because candidates have no INSERT policy on `enrollments`.

It also fetches the profile + resume rows needed for the sidebar completeness ring and
wraps everything in `<AppShell>`.

## The async background job pattern

**Every** feature that processes work in the background follows this shape. Don't
invent a new one per feature.

```
1. Client triggers a Server Action
        ↓
2. Action inserts a row with status:'processing' → toast 1 ("in progress")
        ↓
3. inngest.send(event)   ← fire and forget; the user can navigate away
        ↓
4. Inngest function runs (Anthropic call, etc.), writes results back
   with the SECRET key, flipping status → 'complete'
        ↓
5. Supabase Realtime postgres_changes fires
        ↓
6. Per-domain hook in src/hooks/ catches it → Sonner toast with an action
   button → routes to the result page
        ↓
7. Hook invalidates the relevant queryKeys.* entry
```

**Status enum on each domain table:** `'uploading' | 'processing' | 'complete' |
'failed'` (variants where the domain demands).

**Notification hooks** live in `src/hooks/`, subscribe to `postgres_changes` filtered
by `profile_id=eq.${userId}`, and are mounted **once** in
`components/providers/realtime-notifications.tsx` inside the root layout — so they
survive navigation. Clean up with `supabase.removeChannel(channel)` on unmount.

Currently mounted: `useResumeNotifications`, `useLinkedinNotifications`,
`useApplicationNotifications`, `usePaymentNotifications`, `useJdNotifications`,
`useNotificationFeed`.

**Why this shape:** Realtime beats polling; a layout-mounted hook survives navigation;
Sonner queues toasts natively; and identical scaffolding makes each new async feature
predictable.

### Failure handling in the pattern

- Each Inngest function has an `onFailure` handler that flips the row to
  `status: 'failed'` with a truncated error message. Keep this when adding functions.
- If `inngest.send()` itself throws, the action returns
  `{ kind: "inngest_send_failed", resumeId }` so the UI can offer a **retry button**
  rather than hanging silently. There's also a recovery path for rows stuck in
  `uploading`/`processing`.

## Supabase clients — pick the right one

| Client                           | Key         | RLS          | Use in                               |
| -------------------------------- | ----------- | ------------ | ------------------------------------ |
| `src/lib/supabase/client.ts`     | publishable | enforced     | Client Components, hooks             |
| `src/lib/supabase/server.ts`     | publishable | enforced     | Server Components, Actions, handlers |
| `src/lib/supabase/service.ts`    | **secret**  | **BYPASSED** | Inngest workers, webhook handlers    |
| `src/lib/supabase/anon.ts`       | publishable | enforced     | Unauthenticated public reads         |
| `src/lib/supabase/middleware.ts` | publishable | enforced     | Session refresh in `src/proxy.ts`    |

**The service client bypasses RLS entirely.** It exists because background workers and
webhook handlers have no user session. Using it anywhere reachable from the browser is
an immediate PR rejection.

Do not assume the server client bypasses RLS. It doesn't.

## Testing

There is **no test framework** and no `test` script. What exists instead:

### `.check.ts` self-checks

Ten `assert`-based files colocated with the logic they cover. Run individually:

```bash
npx tsx src/lib/purchase-gate.check.ts
```

| File                                             | Covers                         |
| ------------------------------------------------ | ------------------------------ |
| `src/lib/purchase-gate.check.ts`                 | Gate branch order              |
| `src/lib/jd-quota.check.ts`                      | JD check entitlement           |
| `src/lib/calendly.check.ts`                      | Webhook signature + parsing    |
| `src/lib/cal.check.ts`                           | Cal.com twin (dormant)         |
| `src/lib/dashboard/prescribe.check.ts`           | Dashboard prescription rules   |
| `src/lib/assessment/big-wins.check.ts`           | Big Wins logic                 |
| `src/lib/assessment/career-positioning.check.ts` | Quiz scoring                   |
| `src/lib/assessment/role-clarity.check.ts`       | Role Clarity scoring           |
| `src/data/target-roles.check.ts`                 | Reference data integrity       |
| `src/components/local-date.check.ts`             | Hydration-safe date formatting |

**CI does not run these.** The `ci.yml` "Test (if available)" step is
`continue-on-error: true` against a script that doesn't exist, so it always no-ops.
Wiring these into CI is a cheap, high-value first contribution — see
[`open-items.md`](open-items.md).

### LLM evals

`npm run eval:scorers` (offline, free) and `npm run eval:all`. See
[`services.md`](services.md#anthropic) and [`evals/README.md`](../../evals/README.md).

### Everything else is manual

`npm run type-check`, `npm run check`, and the smoke tests in
[`local-setup.md`](local-setup.md).
