Flows

Three walkthroughs that cover most of the platform: the resume pipeline, a purchase becoming an entitlement, and the assessment → prescription loop.

Jump to: Resume pipeline · Purchase → entitlement · Assessment → prescription

1. Resume upload → parse → score → toast

The canonical instance of the async background-job pattern. Every other background feature is a copy of this shape — don't invent a new one. 

Candidate         Server Action      Inngest         Anthropic      Supabase
    │                   │                │                │             │
    │── upload PDF ────▶│                │                │             │
    │                   │── hash file ──────────────────────────────────▶│
    │                   │◀── duplicate? ────────────────────────────────│
    │                   │                │                │             │
    │                   │── insert row, status:'uploading' ────────────▶│
    │◀── toast 1 ───────│                │                │             │
    │   "in progress"   │                │                │             │
    │                   │── send(resume/uploaded) ──▶│    │             │
    │                   │   fire & forget            │    │             │
    │◀──────────────────│                │           │    │             │
    │  free to navigate away             │           │    │             │
    │                                    │── parse ──────▶│             │
    │                                    │◀── ParsedResume│             │
    │                                    │── score ──────▶│             │
    │                                    │◀── Scoring ────│             │
    │                                    │── write back (SECRET key) ──▶│
    │                                    │   status:'complete'          │
    │                                    │                              │
    │◀════ Realtime postgres_changes ══════════════════════════════════│
    │                                                                   │
    │◀── toast 2, with action button ── useResumeNotifications          │
    │    → invalidates queryKeys.resumes                                │
  1. Upload

    src/app/actions/resume.ts. The file is hashed first — a duplicate short-circuits with "Resume already on file" and no Claude call fires. A different file supersedes the previous row (is_current = false, superseded_at stamped).

  2. Row inserted, first toast

    resumes.status starts at 'uploading'. The user sees immediate feedback and can navigate away.

  3. inngest.send('resume/uploaded')

    Fire and forget. If this throws, the action returns { kind: "inngest_send_failed", resumeId } so the UI offers a retry button rather than hanging. There's also a recovery path for rows stuck in uploading/processing.

  4. parse-resume runs

    src/inngest/functions/parse-resume.ts. Two Claude calls: parse with the cheap model, score with the stronger one. Each step is a step.run(), so a retry resumes rather than restarting. retries: 2, concurrency: { limit: 5 }.

  5. Results written back with the secret key

    The worker has no user session, so it uses createServiceClient(), which bypasses RLS. parsed_json, resume_score, and the prompt version are stored; status flips to 'complete'.

  6. Realtime fires

    useResumeNotifications — mounted once in the root layout, so it survives navigation — catches the postgres_changes event filtered by profile_id=eq.${userId}.

  7. Toast + cache invalidation

    Sonner toast with an action button routing to /resume, and the relevant queryKeys.* entry is invalidated.

On failure

The function's onFailure handler flips the row to status: 'failed' with a truncated parse_error. NonRetriableError is used for "this will never succeed" cases (row missing) so retries aren't burned.

Same shape, different domain: parse-linkedin (LinkedIn PDF exports — and it must leave the OAuth fields linkedin_url, headline, raw_json untouched) and match-jd (a pasted job description scored against the resume, surfaced at /jd-match).

2. Purchase → payment → entitlement

This path has never completed end to end. payments and enrollments were both 0 rows at last audit. Everything below is as-designed, not as-verified. 

Candidate      /api/stripe/checkout      Stripe      /api/stripe/webhook   Supabase
    │                  │                    │                 │              │
    │── POST {priceId} ▶│                    │                 │              │
    │                  │── assertAllowedPriceId() ─────────────────────────▶ │
    │                  │   derives subscription vs one_time server-side      │
    │                  │                    │                 │              │
    │                  │── create customer if needed ────────▶│              │
    │                  │── cache stripe_customer_id ───────────────────────▶ │
    │                  │── create Checkout Session ──────────▶│              │
    │◀── redirect URL ─│                    │                 │              │
    │                                       │                 │              │
    │══ pays on Stripe's hosted page ══════▶│                 │              │
    │                                       │── webhook ─────▶│              │
    │                                       │                 │── verify sig │
    │                                       │                 │── dedupe on  │
    │                                       │                 │   event_id ─▶│
    │                                       │                 │              │
    │                                       │      handleCheckoutCompleted   │
    │                                       │                 │── payments ─▶│
    │                                       │                 │── enrollments│
    │                                       │                 │   (+ bundle  │
    │                                       │                 │    fan-out) ▶│
    │◀── /checkout/success ─────────────────│◀── 200 ok ──────│              │
  1. Client POSTs { priceId }

    That's the entire request body.

  2. The price is validated server-side

    assertAllowedPriceId() checks it against coaching_products.stripe_price_id and derives subscription vs one_time from it. A client cannot force the mode or pay an arbitrary price.

  3. Stripe customer ensured

    Created if absent, then cached on profiles.stripe_customer_id for the portal and webhook lookups.

  4. Checkout Session created; client redirects

    Success and cancel URLs are built from NEXT_PUBLIC_SITE_URL — which is why a wrong value in production sends paying customers to localhost.

  5. Webhook: verify, then dedupe

    Raw body + Node runtime are required for signature verification. The event is recorded in stripe_webhook_events and the handler short-circuits if processed_at is already set — Stripe redelivers.

  6. handleCheckoutCompleted

    Inserts a payments row (unique-violation tolerant), then upserts enrollments.

  7. Bundle fan-out

    A bundle grants its own enrollment plus one per product in bundle_contents, so both "what did they buy" and "what can they access" stay answerable. Upserted with ignoreDuplicates — on conflict do nothing per row — so redelivery is a no-op and a buyer who already owns one contained SKU still gets the rest. A plain insert would fail the whole batch on 23505.

Two design decisions worth knowing

Handler errors return 5xx on purpose so Stripe retries; the error is stored on the stripe_webhook_events row. Unknown event types are recorded and acked with 200 — a 4xx would make Stripe retry forever.

The bundle's own enrollment row is load-bearing. The quick-add SKUs in bundle_contents are a coarser, cheaper repackaging and don't cover everything a tier advertises — so the fan-out can't be the whole entitlement story.

Then: the purchase gate reads it

src/app/(app)/layout.tsx

  no user ──────────────────────────────────▶ redirect('/login')
  role === 'employer' ──────────────────────▶ redirect('/employer')
  needsPurchase({ enabled, isAdmin, hasEnrollment }) ─▶ redirect('/invite')

src/lib/purchase-gate.ts   (pure — see purchase-gate.check.ts)

  !enabled   → false   gate off is fully inert, whatever the role
  isAdmin    → false   admins are the ones who'd have to unlock it
  otherwise  → !hasEnrollment

hasAnyEnrollment() in src/lib/coaching.ts reads enrollments — never user metadata, which the browser session can write itself. A migration (20260903000000_enrollments_no_self_grant.sql) removes the candidate INSERT policy, so entitlement can only be granted by server code that checked something first. There are exactly two such writers: 

  handleCheckoutCompleted()   ← a completed Stripe payment
  redeemInviteCode()          ← a valid BETA_INVITE_CODE at /invite
                                grants a comp "Beta Access" enrollment

  both write on the SERVICE-ROLE client, and both land in `enrollments`

The beta code is also registered as a 100%-off Stripe promotion code, so a tester who runs real checkout instead arrives at the same place via the webhook. Either way, enrollments stays the single entitlement source.

3. Assessment → scores → dashboard prescription

How the platform decides what to recommend selling to a given candidate. This is the qualification-and-warming layer that feeds 1:1 coaching. 

  ┌─ Career Positioning Assessment ─┐   public, pre-signup, 18 questions
  │  lives in CODE, not the DB      │   → results land on `leads`
  └─────────────────────────────────┘

  ┌─ Career Identity Blueprint ─┐
  │  Big Wins                   │  seeded in `assessments` by migration
  │  Role Clarity               │  answers → `assessment_responses`
  └─────────────────────────────┘  derived → `candidate_scores`
                │
                ▼
      fetchDashboardSignals()  ── src/lib/dashboard/signals.ts
                │
                │  Blueprint dimensions (7 × 0–100)
                │  resume_score · linkedin profile_score · latest JD ats_score
                │  owned product names (from enrollments)
                ▼
        prescribe()  ── src/lib/dashboard/prescribe.ts
                │
                │  RULES, NOT AN LLM
                │  matches on product NAME, not id
                │  never prescribes something already owned
                │  a rule whose product isn't in the catalog is SKIPPED
                ▼
      one product + a `reason` string, shown on the dashboard

Why rules and not an LLM

Straight from the source: this is a ranking-and-explanation problem over a fixed 11-row catalog, and a rules table is auditable, free, and instant. Promote to LLM-assisted only if the rules demonstrably misfire.

Rules match on product name so the seeded catalog can be edited in admin without a code change, and a rule pointing at a product that isn't in the catalog is skipped rather than rendered as a dead CTA.

The reason strings in prescribe.ts are shown to candidates verbatim and have never been reviewed by anyone with voice authority. See open-items.md.

Alongside the prescription, the dashboard composes buildProfileSteps() (the completeness checklist behind the sidebar ring) and computeNudges() (time-sensitive prompts — interviewing applications, stale enrollments). All three are pure functions; only prescribe has a .check.ts.

The intake gate sits in front of all of it

Resume upload is required before dashboard access, and it stays that way even with no job board behind it — building the candidate list is the point. That's rule 3 of the pivot, and it isn't up for re-litigation.
