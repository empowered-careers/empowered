Architecture

How the code is organized, and the four conventions a new contributor is most likely to violate by accident.

Full detail: docs/handover/architecture.md.

The four conventions

Each is enforced by review, not by the compiler.

1. Every authenticated route is a Server Component entry

"No SEO needed" does not mean "no Server Component." Even noindex pages use a Server Component as the page entry.

LayerResponsibility
page.tsx
Server Component		 Auth check + redirect(), initial data fetch, metadata
*-client.tsx
Client Component		 State, events, TanStack Query hydrated from initialData, Realtime, modals

Perf — data ships with the HTML, no spinner on first paint. Auth — server-side redirect runs before render, no flash of protected content. RLS — the server client carries the user's session, so policies just work. No DTO layer: pass Supabase row types straight through.

2. Never import database.types.ts directly

It's generated by npm run supabase:types and is not an import target. Every alias lives in src/types/db.ts. 

// ✗ never
type Status = Database["public"]["Enums"]["resume_status"];

// ✓ always
import type { ResumeStatus } from "@/types/db";

For column-subset selects, add both the SELECT string (e.g. JOB_CARD_COLUMNS) and the matching Pick<> type to db.ts, and use the constant in .select(...) so they can't drift. When you touch an unfamiliar table, step one is adding its aliases to db.ts.

3. All mutations are Server Actions

Everything in src/app/actions/ — 15 files, one per domain. After a Server Action succeeds, invalidate the relevant TanStack Query key.

4. Query keys come from src/lib/query-keys.ts

Never hardcode a string array as a query key. Add it to queryKeys and import it.

The (app) layout does three gates, in order

  1. Auth

    No user → redirect('/login')

  2. Role

    role === 'employer' → redirect('/employer')

  3. Purchase

    If PURCHASE_GATE_ENABLED === "true" and the user is neither an admin nor an enrollment holder → redirect('/invite'). Entitlement is read from enrollments, never from user metadata, which the browser session can write itself.

The async background-job pattern

Every feature that processes work in the background follows this shape. Don't invent a new one per feature.

  1. Client triggers a Server Action
  2. Action inserts a row with status: 'processing'

    Toast 1 — "in progress"

  3. inngest.send(event)

    Fire and forget. The user can navigate away freely.

  4. Inngest function runs

    Calls Anthropic, writes results back with the secret key, flips status → 'complete'

  5. Supabase Realtime postgres_changes fires
  6. Per-domain hook catches it

    Sonner toast with an action button routing to the result page

  7. Hook invalidates the relevant queryKeys.* entry

Status enum on each domain table: 'uploading' | 'processing' | 'complete' | 'failed', with variants where the domain demands.

Notification hooks live in src/hooks/, subscribe to postgres_changes filtered by profile_id=eq.${userId}, and are mounted once in components/providers/realtime-notifications.tsx inside the root layout — so they survive navigation. Clean up with supabase.removeChannel(channel) on unmount.

Currently mounted: useResumeNotifications, useLinkedinNotifications, useApplicationNotifications, usePaymentNotifications, useJdNotifications, useNotificationFeed.

Failure handling is part of the pattern.

Each Inngest function has an onFailure handler that flips the row to status: 'failed' with a truncated error. If inngest.send() itself throws, the action returns { kind: "inngest_send_failed", … } so the UI offers a retry button rather than hanging silently.

Supabase clients — pick the right one

ClientKeyRLSUse in
supabase/client.tspublishableenforcedClient Components, hooks
supabase/server.tspublishableenforcedServer Components, Actions, handlers
supabase/service.tssecretBYPASSEDInngest workers, webhook handlers
supabase/anon.tspublishableenforcedUnauthenticated public reads
supabase/middleware.tspublishableenforcedSession refresh in src/proxy.ts

The service client bypasses RLS entirely. It exists because background workers and webhook handlers have no user session. Using it anywhere reachable from the browser is an immediate PR rejection. And the server client does not bypass RLS — don't assume it does.

Testing

There is no test framework and no test script. What exists instead:

Nine .check.ts self-checks

assert-based files colocated with the logic they cover. Silent exit = pass. 

npx tsx src/lib/purchase-gate.check.ts
FileCovers
lib/purchase-gate.check.tsGate branch order
lib/jd-quota.check.tsJD check entitlement
lib/calendly.check.tsWebhook signature + parsing
lib/cal.check.tsCal.com twin dormant
lib/dashboard/prescribe.check.tsDashboard prescription rules
lib/assessment/big-wins.check.tsBig Wins logic
lib/assessment/career-positioning.check.tsQuiz scoring
lib/assessment/role-clarity.check.tsRole Clarity scoring
data/target-roles.check.tsReference data integrity

CI does not run these. The ci.yml "Test (if available)" step is continue-on-error: true against a script that doesn't exist, so it always no-ops. Wiring them in is a cheap, high-value first contribution.

LLM evals

npm run eval:scorers   # offline replay — free, no API key
npm run eval:all       # adds parser suites (no-op without local PDF fixtures)

Gates on rubric pass rate ≥ 0.95, pairwise accuracy ≥ 0.85, label agreement ≥ 0.80. Parser suites ship with no committed inputs on purpose — a realistic resume PDF is somebody's actual resume, and that PII doesn't belong in the repo.

Everything else is manual

npm run type-check
npm run check        # ESLint + Prettier — what CI runs

Plus the smoke tests in local-setup.md.
