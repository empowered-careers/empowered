Third-party services

Every external dependency: what it does here, which files touch it, and exactly what breaks when its variable is unset.

The posture: optional and inert

Only Supabase is required for the app to boot. Every other integration degrades quietly when its variable is unset. This is deliberate, so the app runs locally without every vendor provisioned — don't "fix" it by making them required in env.ts.

Supabase live

Everything persistent: PostgreSQL (28 tables), Auth (email + Google + LinkedIn OAuth), Storage (2 buckets), Realtime, and RLS — which is the actual authorization model, not a nice-to-have.

Files: five clients in src/lib/supabase/ — client, server, service, anon, middleware.

Variables: NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY (both required to boot), SUPABASE_SECRET_KEY (bypasses RLS, server-only).

Uses the publishable/secret key naming, not legacy anon/service_role — see MIGRATION.md.

Vercel live

Hosting, preview deploys, and Web Analytics (@vercel/analytics in src/app/layout.tsx). Deploys on merge to main. Current deployment: empowered-orcin.vercel.app.

The environment-parity trap

Every server-side variable must be set in Vercel, not just .env.local. Inngest Cloud runs the workers by calling the Vercel function — so a local-only ANTHROPIC_API_KEY or SUPABASE_SECRET_KEY means every production parse and score fails while local dev looks perfectly healthy.

Also: NEXT_PUBLIC_SITE_URL must be the real domain. Stripe Checkout builds its success/cancel URLs from it, so a wrong value sends paying customers to localhost.

Inngest live

All asynchronous work. App id empowered-careers, served from src/app/api/inngest/route.ts, event schemas typed with Zod in src/inngest/client.ts.

FunctionTriggerDoes
parse-resumeresume/uploadedPDF → Claude parse → Claude score → write back
parse-linkedinlinkedin/uploadedSame shape for LinkedIn PDF exports
match-jdjd/submittedScores a pasted JD against the resume
sweep-inactivecron 0 7 * * *Fires 7- and 30-day inactivity events to Loops

Local dev needs no keys. npm run dev sets INNGEST_DEV=1, pointing the client at npm run inngest:dev (GUI on localhost:8288).

Production needs two different keys: INNGEST_SIGNING_KEY is Inngest Cloud proving it may invoke your endpoint; INNGEST_EVENT_KEY is your app proving it may send events. Having only the signing key is a real and confusing failure — the endpoint syncs green, but inngest.send() throws.

The most-forgotten operational step. After every deploy that adds or changes a function: 

curl -X PUT https://<your-domain>/api/inngest
# → {"message":"Successfully registered","modified":true}

Conventions: async work goes through Inngest (no raw API routes for long-running work); register in the serve({ functions: [...] }) array; concurrency is capped at { limit: 5 } per function — don't remove it; every function needs an onFailure handler that flips the row to failed; use NonRetriableError for "this will never succeed".

The prompt-version strings are stamped onto every parsed row. Bump them whenever you change a prompt or the rubric — otherwise old and new results are indistinguishable in the data.

Run the evals before changing a prompt: npm run eval:scorers (offline, free). --record and --live cost money.

The purchase gate

PURCHASE_GATE_ENABLED=true requires a signed-in candidate to hold an enrollment before the app opens. Anything else — including unset — is fully inert. Entitlement is read from enrollments, never from user metadata, which the browser session can write itself. Admins always bypass.

The private beta invite code

BETA_INVITE_CODE (e.g. ECTEST100). There are two ways a tester gets in, and both end at the same place — a row in enrollments:

  1. Enter the code at /invite. redeemInviteCode() grants a comp "Beta Access" enrollment.
  2. Run real Stripe checkout using the same string as a 100%-off promotion code. The webhook then grants the enrollment.

Redemption writes on the service-role client. After migration 20260903000000, candidates have no INSERT policy on enrollments — entitlement can only be granted by server code that checked something first: the code here, or a completed payment in the webhook.

matchesInviteCode() is case- and whitespace-insensitive (testers paste it out of an email) and never matches when BETA_INVITE_CODE is unset or blank, so a blank form can't unlock anything. /invite hides the form entirely when no code is configured, falling back to the purchase route.

Migration 20260903010000_beta_access_product.sql seeds the "Beta Access" product — enrollments.product_id is NOT NULL, so redemption needs something to enroll in. It's is_active = false, keeping it out of /pricing, the catalog, and dashboard signals, which all filter on that flag.

Loops wired, not live

The app already fires 14 events from Server Actions and Inngest functions — candidate.signup, candidate.resume_uploaded, candidate.course_purchased, candidate.session_booked, candidate.enrollment_completed, candidate.inactive_7d, candidate.inactive_30d, plus the lead.* and assessment.* events.

No sequences exist in Loops to receive them, so nothing sends. Creating them is an ops task, not an engineering one. Code: src/lib/loops/client.ts.

Calendly blocked

Candidates book coaching sessions; the webhook records them into coaching_sessions. Code: src/lib/calendly.ts, src/app/api/calendly/webhook/route.ts.

Blocked on one variable. CALENDLY_WEBHOOK_SECRET has never been set, so the route returns 503 and no booking has ever been recorded. Booking URLs are set on all 8 session products — candidates can book, the platform just doesn't know.

The non-obvious design

All session products deliberately share a single Calendly event type. Bookings are matched to enrollments on the utm_content query parameter — which carries the enrollment id — not on the event slug. Duplicate booking URLs across products are correct, not a bug.

Cal.com dormant

src/lib/cal.ts and src/app/api/cal/webhook/route.ts are a complete, unused twin of the Calendly integration, gated behind CAL_WEBHOOK_SECRET. No account behind it. It exists as a swap-in alternative. Leave it alone.

GitHub Actions live

ci.yml runs on push and PR to main: type-check → check → build, on Node 20.11.0. The build step uses placeholder Supabase values, so CI needs no real secrets.

The final "Test (if available)" step is continue-on-error: true against a test script that doesn't exist — it always no-ops. CI does not run the nine .check.ts self-checks.
